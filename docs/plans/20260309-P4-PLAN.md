# P4 Development Plan

Date: 2026-03-09
Scope: IoT integration, advanced personalization, multi-device sync, screen agent foundations
Execution mode: strict TDD only

## Goals

P4 focuses on turning Prometheus from a single-session assistant into a context-aware system that can:

1. discover and manage trusted devices in the local environment,
2. learn durable user preferences with explicit consent boundaries,
3. sync identity and state across devices safely,
4. prepare the execution substrate for future screen-agent workflows.

## Non-negotiable TDD rules

Every P4 task follows:

1. `Red`: add a failing test first.
2. `Green`: implement the smallest behavior needed to pass.
3. `Refactor`: improve structure without changing behavior.

Reference: `docs/engineering/tdd-protocol.md`

## Delivery order

### Track A: IoT foundation

`P4-T01` Device discovery abstraction
- Add pluggable discovery backends.
- Merge and deduplicate scan results.
- Preserve last known device inventory.

`P4-T02` Secure pairing state machine
- Pairing initiation, confirmation, cancellation, unpairing.
- Track trusted device state explicitly.
- Reject invalid confirmation flows.

`P4-T03` Generic device command routing
- Register adapters by protocol.
- Register devices discovered or persisted from Track A.
- Route `turn_on`, `turn_off`, `set_property`, `get_state` deterministically.

`P4-T04` IoT workflow bridge
- Convert workflow actions into controller calls.
- Add permission-aware guard rails before execution.

### Track B: Personalization foundation

`P4-T05` Durable user profile extraction
- Infer language, display name, interests, and explicit preferences from conversation text.
- Keep updates deterministic and testable.
- Persist profile snapshots locally.

`P4-T06` Persona engine activation
- Load, update, list, and switch personas.
- Guarantee exactly one active persona after valid activation.

`P4-T07` Consent-aware prompt shaping
- Apply profile and persona only when corresponding consent exists.
- Expose a prompt-context builder for orchestrator integration.

### Track C: Multi-device sync

`P4-T08` Device identity registry
- Stable device records for sync participants.
- Trust state, last-seen metadata, and local capability flags.

`P4-T09` Sync envelope and conflict policy
- Define sync payloads for profile, sessions, and settings.
- Add deterministic merge rules for last-write-wins fields and append-only history.

### Track D: Screen-agent preparation

`P4-T10` Screen action model
- Typed action graph for observe, focus, click, type, extract.
- No GUI automation yet; only validated action plans and permissions.

## Implementation sequence for the current cycle

This cycle implements the first core slice:

1. `P4-T01` Device discovery abstraction
2. `P4-T02` Secure pairing state machine
3. `P4-T03` Generic device command routing
4. `P4-T05` Durable user profile extraction
5. `P4-T06` Persona engine activation

These tasks are chosen first because they unblock later server, FFI, workflow, and sync work while staying local, deterministic, and unit-test friendly.

## Test matrix

### Unit

- discovery backend merging and deduplication
- pairing state transitions
- controller routing and command validation
- persona load and switch semantics
- profile extraction heuristics and persistence serialization

### Integration

- discovered device -> paired device -> routed command
- profile update -> save -> reload
- persona + profile preparation for future orchestrator injection

### Deferred to later slices

- real mDNS or SSDP network discovery
- actual protocol adapters such as Matter or HomeKit
- end-to-end mobile and desktop sync transport
- real screen automation

## Acceptance criteria for this cycle

1. All newly added P4 tests fail before implementation and pass after implementation.
2. No `todo!()` remains in the modules touched by this cycle.
3. `cargo test -p prometheus-core` stays green.
4. Public APIs remain deterministic and offline-testable.
